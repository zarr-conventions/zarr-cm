# `zarr-cm` 0.5

This post announces the v0.5 release of
[`zarr-cm`](https://zarr-cm.readthedocs.io/en/latest/)[^1]. It's also our first
blog post; in my opinion, `zarr-cm` has become useful enough to be worth
blogging about. So this post will open with some background about Zarr
conventions, and how `zarr-cm` fits in the picture, before getting to the v0.5
release highlights.

If you already know what Zarr conventions are and just want the headline
changes, this release adds [node-aware validation](#validation-functions),
[forgiving reads of declarations found in the wild](#reading-what-people-actually-wrote),
and [revision pinning](#knowing-what-youll-write). See the
[release notes](../../release-notes.md) for the itemized list.

## Zarr Conventions

In October of 2025 a bunch of Zarr-oriented folks gathered in Rome for
[the first Zarr summit](https://zarr.dev/zarr-summit-2025/). We had a great
time, and we got a lot done! Among the many useful developments was
[`zarr-conventions`](https://github.com/zarr-conventions/): a specification for
registering useful data annotations in the `attributes` field of Zarr array and
group metadata documents without requiring much central coordination. The
concept of "useful data annotation" is not precisely defined, but operationally
that description works well for things like:

- declaring which
  [coordinate reference system](https://en.wikipedia.org/wiki/Spatial_reference_system)
  (CRS) applies to data in Zarr arrays and groups
  ([`proj` convention](https://github.com/zarr-conventions/proj))
- declaring how multiple Zarr arrays comprise a multiscale pyramid
  ([`multiscales` convention](https://github.com/zarr-conventions/multiscales))
- associating a license with some Zarr data
  ([`license` convention](https://github.com/clbarnes/zarr-convention-license))

... and more. See the
[`zarr-conventions` GitHub page](https://github.com/zarr-conventions/) for the
larger list the example conventions were drawn from.

If you work with Zarr data and your data has structured information that you
want consumers to find easily, then Zarr conventions are worth a look! The next
section explains how they work.

### Convention Anatomy

Each convention combines a structured JSON object that _declares_ the convention
with a rule that _implements_ the convention. This is a classic
`(tag, tagged thing)` relationship. The rule is often a requirement that the
`attributes` field of the Zarr array or group metadata contains some key or set
of keys, along with optional constraints on other fields or properties of the
Zarr array or group.

Whatever the rule required by the convention, a Zarr array or group that uses
these conventions _must_ have a top-level `zarr_conventions` key in its
`attributes` field. That `zarr_conventions` key holds a JSON array that contains
the declarations of each convention implemented by the Zarr array or group. The
`zarr_conventions` field is purely for declaring the presence of conventions;
the convention metadata itself, if any, is expressed elsewhere in the
`attributes` field of the Zarr array or group.

For example, here's a JSON snippet that demonstrates the `license` convention:

```json
{
  // this is metadata for a Zarr v3 group
  "node_type": "group",
  "zarr_format": 3,
  "attributes": {
    // the actual convention
    "license": { "spdx": "CC0" },
    // the convention declaration
    "zarr_conventions": [
      {
        "schema_url": "https://raw.githubusercontent.com/clbarnes/zarr-convention-license/refs/tags/v1/schema.json",
        "spec_url": "https://github.com/clbarnes/zarr-convention-license/blob/v1/README.md",
        "uuid": "b77365e5-2b0c-4141-b917-c03b7c68e935",
        "name": "license",
        "description": "License specifier for Zarr data"
      }
    ]
  }
}
```

There's not _much_ complexity on display in this example, but there are some
details, like the literal UUID string, that I would describe as "fiddly". A typo
in the UUID would be very hard to spot.

With the [GeoZarr](https://geozarr.org/) project coalescing around a core of
[Zarr conventions](https://geozarr.org/conventions.html), we expect readers for
Zarr conventions to proliferate. So a few months ago I decided to create a
simple Python package for working with Zarr convention metadata. That's
`zarr-cm`.

## `zarr-cm`

`zarr-cm` is a Python package that delivers the simplest possible tools
necessary to get Zarr conventions right. Caveat: Zarr conventions are new, so I
don't think we know yet what "getting it right" means. With that in mind I have
been adding features to `zarr-cm` incrementally, adding features _I_ needed
while working on a GeoZarr export tool as part of the
[EOPF-Explorer](https://explorer.eopf.copernicus.eu/) project.

### Intended Audience

I don't always like the distinction between "users" and "developers" (developers
_are_ users!) but in this instance I can say that `zarr-cm` is a tool for
developers, e.g. people who will maintain Python software that reads or writes
Zarr data using Zarr conventions.

### Features

As stated above, a Zarr convention defines two things: a JSON object that
declares the convention, and the convention itself, which is a rule for a Zarr
array or group. The Zarr conventions spec doesn't formally define a scope for
the rules, but so far most rules govern the contents of the `attributes` field
of the Zarr array or group declaring the convention[^2].

That means `zarr-cm` should define useful types for modelling these two things,
and type-safe transformations for making useful Zarr-conventional data.

#### Core types

The first feature `zarr-cm` provided was `TypedDict` types for the core JSON
data structures. For each convention we provided (and still provide):

1. A `TypedDict` for the convention declaration.
2. A `TypedDict` for the convention itself.
3. A `TypedDict` for the shape of the `attributes` field of a Zarr array or
   group that complies with the convention.

A set of `TypedDict` types is a simple, low-commitment API with a well-defined
scope. For software that works with JSON-centric specifications, I often start
with `TypedDict`s and keep them updated as the library evolves. Even if the
people using the library never name these types themselves, the types keep our
own test data well formed. And anyone who has to build Zarr-convention-compliant
metadata documents gets the benefit directly.

#### Creation functions

`zarr-cm` defines functions that produce instances of the canonical `TypedDict`
types. Each Zarr convention has a `create` function that takes per-convention
keyword arguments and produces a dict satisfying the type of the convention.
Alongside it, `create_convention_attrs` combines the convention data with the
convention declaration, producing a complete `attributes` dict.

Both produce _syntactically_ valid conventions. Semantic validity requires a bit
more work — see below.

Together they rebuild the `attributes` field of the `license` document from
earlier, with the declaration — `uuid` and all — filled in for you:

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from zarr_cm import license

# Just the convention's own keys
print(license.create(spdx="CC0-1.0"))
#> {'spdx': 'CC0-1.0'}

# The same data, plus the declaration in `zarr_conventions`
attributes = license.create_convention_attrs(spdx="CC0-1.0")
print(sorted(attributes))
#> ['license', 'zarr_conventions']
print(attributes["zarr_conventions"][0]["uuid"])
#> b77365e5-2b0c-4141-b917-c03b7c68e935
```

<!-- blacken-docs:on -->

`create_convention_attrs` is new in v0.5.

#### Validation functions

_The Zarr-node-aware functions are new in the v0.5 release of `zarr-cm`_

Zarr conventions often define rules governing the values assigned to fields
defined in the convention. Many of these rules can't be expressed in Python's
type system[^3], so functions are necessary for checking them.

Some rules can't be checked from the attributes alone at all, because they
depend on the _kind_ of Zarr node the convention is attached to. The `spatial`
convention is the motivating case: `spatial:dimensions`
[is required](https://github.com/zarr-conventions/spatial#spatialdimensions)
when the convention appears on an array, but a group may legitimately carry
other `spatial:` keys without it, e.g. a bounding box over child arrays that
don't share a single grid.

As of v0.5, `zarr-cm` has new routines that validate conventions in the context
of the metadata document (array or group) in which they are declared. Previously
`spatial.create()` demanded `dimensions=` unconditionally, which is wrong for
groups; now the key is optional at the attribute level, and the array
requirement is enforced where the node type is actually known. So `zarr-cm` now
distinguishes internal consistency checks (`validate`, over an attributes dict)
from node-level checks (`validate_array_metadata`, `validate_group_metadata`,
and `validate_node_metadata`, over a whole `zarr.json` document):

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from zarr_cm import spatial

# A footprint with no dimensions: fine at the attribute level ...
attributes = spatial.create_convention_attrs(bbox=[-180.0, -90.0, 180.0, 90.0])
group = {"zarr_format": 3, "node_type": "group", "attributes": attributes}

# ... and fine on a group.
print(spatial.validate_node_metadata(group)["node_type"])
#> group

# The very same attributes on an array are not valid.
try:
    spatial.validate_array_metadata({**group, "node_type": "array"})
except ValueError as exc:
    print(exc)
    #> 'spatial:dimensions' is required on array nodes
```

<!-- blacken-docs:on -->

When one of these node metadata-aware functions succeeds, we have gain some
information about the type of our value: in addition to being an array / group
metadata document, we also know that the `attributes` of the metadata document
is consistent with a particular Zarr convention. By making the array / group
metadata document generic over the contents of `attributes`, we can encode
validation in the type domain. A convention-bearing document has type
`Metadata[AttrsT]`, and validating narrows that parameter to the convention's
own attrs type. A function can then _require_ a validated document in its
signature, and handing it an unvalidated one is a type error rather than a
runtime surprise:

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from collections.abc import Mapping

from zarr_cm import GroupMetadata, JSONValue, SpatialConventionAttrs, spatial

def write_group(node: GroupMetadata[SpatialConventionAttrs]) -> str:
    # `attributes` is spatial's TypedDict here, not an untyped JSON blob
    return f"writing, bbox={node['attributes'].get('spatial:bbox')}"

group: GroupMetadata[Mapping[str, JSONValue]] = {
    "zarr_format": 3,
    "node_type": "group",
    "attributes": spatial.create_convention_attrs(bbox=[0.0, 0.0, 1.0, 1.0]),
}

print(write_group(spatial.validate_group_metadata(group)))
#> writing, bbox=[0.0, 0.0, 1.0, 1.0]
```

<!-- blacken-docs:on -->

The narrowed type records that validation _happened_, not that the document
stays valid forever — the returned mapping is still mutable. We might get some
respite when `frozendict` enters the Python standard library, but until then
mutable dicts is just something we have to accept with in this package.
Similarly, Python today doesn't have intersection types, so narrowing doesn't
accumulate: validating against `spatial` and then `proj` leaves you with
`proj`'s type alone.

#### Combination functions

A strength of the Zarr conventions framework is that separate Zarr conventions
can be composed as long as they use disjoint keys in the `attributes` field of a
Zarr array or group. Logically that defines an `insert` operation, which adds a
particular Zarr convention to a dict destined for a Zarr array or group's
`attributes` field, and an inverse `extract` that pops a complete Zarr
convention back out of a dict that contains it. `create_many` and `extract_all`
are the multi-convention forms:

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from zarr_cm import create_many, extract_all, multiscales, proj, spatial

attrs = create_many(
    {
        "proj": proj.create(code="EPSG:27704"),
        "spatial": spatial.create(dimensions=["y", "x"]),
        "multiscales": multiscales.create(layout=[{"asset": "0"}]),
    }
)
print([cmo["name"] for cmo in attrs["zarr_conventions"]])
#> ['proj:', 'spatial:', 'multiscales']

remaining, extracted = extract_all(attrs)
print(remaining, sorted(extracted))
#> {} ['multiscales', 'proj', 'spatial']
```

<!-- blacken-docs:on -->

In v0.5, `insert` got a fix. It now correctly merges the `zarr_conventions`
array rather than replacing it. Pre-existing declarations are unaffected, and
the inserted convention's entry supersedes any prior declaration of that same
convention in place. Inserting a second convention used to quietly discard the
first one's declaration, which was a data-loss bug.

#### Reading conventional data

The previous section covered the writing path, where you control the output.
Reading is different: you get whatever the writer produced, and the ecosystem is
fresh enough that some data in in the wild has declarations that don't quite
line up with the spec.

Between the conventions' first drafts and their `v0.1` releases, the spec
READMEs published example declarations whose `schema_url` pointed at a
`refs/tags/v1` tag that was never actually created. Tools integrated during that
window copied those examples faithfully, so documents declaring dead URLs exist
and are still being written. Separately, the published `v0.1` tag URLs differ
textually from the commit-pinned URLs `zarr-cm` writes, even though they point
at the same schema.

We handle this by ensuring that each revision recognizes a _set_ of
`schema_url`s — its canonical one plus aliases — and a declaration may identify
its convention by `schema_url` alone, with no `uuid`:

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from zarr_cm import detect_revisions, extract_all, proj

# A document from the draft era: dead tag URL, no uuid at all
attrs = {
    "proj:code": "EPSG:4326",
    "zarr_conventions": [
        {
            "schema_url": "https://raw.githubusercontent.com/zarr-conventions/proj/refs/tags/v1/schema.json"
        }
    ],
}

print(detect_revisions(attrs))
#> {'proj': 'r2'}
_, extracted = extract_all(attrs)
print(extracted["proj"])
#> {'proj:code': 'EPSG:4326'}
```

<!-- blacken-docs:on -->

The recognized set is not open. A URL outside it fails loudly instead of being
guessed at — an unknown _future_ revision is never silently misread as one we
happen to know:

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from zarr_cm import extract_all, proj

attrs = {
    "proj:code": "EPSG:4326",
    "zarr_conventions": [
        {"uuid": proj.UUID, "schema_url": "https://example.com/nope.json"}
    ],
}

try:
    extract_all(attrs)
except ValueError as exc:
    print(exc)
    """
    the 'proj' convention declares an unsupported schema_url: 'https://example.com/nope.json'
    """
```

<!-- blacken-docs:on -->

#### Knowing what you'll write

We should be tolerant in what we accept, but strict in what we produce.
`latest_revisions()` reports which revision each revisioned convention writes by
default, and `convention_metadata()` returns the declaration a convention will
emit. Downstream packages can pin against these and notice when a `zarr-cm`
upgrade changes what lands on disk, instead of reaching into the convention
modules:

<!-- blacken-docs:off -->
<!-- prettier-ignore -->
```python
from zarr_cm import convention_metadata, latest_revisions

print(latest_revisions())
#> {'proj': 'r3', 'spatial': 'r3', 'multiscales': 'r2'}

print(convention_metadata("proj")["name"])
#> proj:
```

### Roadmap

#### Attribute-based accessors

Today the APIs in `zarr-cm` create and refine Python dicts. That's great for
folks working with Python dicts, but developers working on user-facing APIs
probably want to expose the structure of a given Zarr convention using a Python
object that supports attribute-based access. That suggests that each Zarr
convention gains a simple Python
[`dataclass`](https://docs.python.org/3/library/dataclasses.html) definition,
one that serializes to and from the JSON-friendly `TypedDict` types we have
already defined and supports attribute access like `attrs.license.spdx` instead
of `attrs["license"]["spdx"]`.

While an attribute-access-based API is indeed nice for a _single_ convention,
it's complicated when multiple conventions are combined, because the attribute
names of a combined convention are a function of the conventions being merged.
So evolving beyond types + functions for plain dicts will take some work, or a
clarifying use case that defines the exact design we need.

We may also want to delegate class-based APIs to downstream packages. A project
like the [GeoZarr Toolkit](https://github.com/zarr-developers/geozarr-toolkit)
is probably the ideal place to define e.g. `GeoZarrGroup` and `GeoZarrArray`
classes, which can expose the full range of possible GeoZarr-flavored attributes
alongside IO-ful operations like reading chunks and creating new arrays. That's
just some forward-looking speculation from me.

If you're building on Zarr conventions and hit something `zarr-cm` makes harder
than it should be, that's the clarifying use case I'm looking for —
[open an issue](https://github.com/zarr-conventions/zarr-cm/issues).

[^1]:
    The "cm" in `zarr-cm` is short for "convention metadata" or "conventional
    metadata".

[^2]:
    The `multiscales` convention defines how a collection of Zarr arrays
    comprises a semantically meaningful unit. That convention uses string paths
    to refer to Zarr arrays. If such a string resolves not to a Zarr array but
    rather to a Zarr group, then this is a violation of the convention. Thus
    _full_ compliance with the `multiscales` convention is a matter that extends
    beyond the structure of the `attributes` of the Zarr node where the
    convention is declared.

[^3]:
    We could model "type with at least one of fields A, or B, or C" with a union
    like `TypeWithA | TypeWithB | TypeWithC`, but this generates really
    unhelpful type checker output.
